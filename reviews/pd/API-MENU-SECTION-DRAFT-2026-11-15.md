## 二、建议新增（3 段，插在 §2.1 的「忌口选项的全量 key 见附录 D」之前）

### A. 份量形态 `serving_mode`

> **一道菜在一餐里扮演什么角色。** 四态枚举：`combo` / `single` / `component` / `plate`。
> 这是实测菜单带来的新维度——原型期只有「主食 × 主菜 × 素菜」一种结构，
> 真实菜单里一份盖浇饭本身就是一整餐，不能再给它配主食。

| 枚举 | 现实是什么 | 引擎怎么处理 | 当前道数 |
|---|---|---|---|
| `combo` | 一楼中晚餐：拿盘选几样，每样按标价牌累加 | 参与组合，与主食/主菜/素菜各取其一 | 25 |
| `single` | 二楼成品餐与一楼面点：点一碗面 / 一盒饭就是**一整餐** | 自成一套，**不得再配主食** | 258 |
| `component` | 健康餐食材、麻辣烫配菜与汤底：自己在柜子里挑几样配主食 | 自由组合（麻辣烫是「汤底必选 + 配菜任选」的三段式） | 76 |
| `plate` | 一楼早餐自选线：拿盘称重、不可单点 | 不进 `combos`，只给配盘建议 | 25 |

> 缺省按 `combo` 处理（原型 55 道本就是这个结构，缺省成别的会让存量行为突变）。

### B. 结算方式 `pricing_mode`

> **份量能不能说死。** 两态枚举：`fixed` / `weigh`。
> 它直接决定**热量的口径**——`weigh` 的菜份量现场定，`kcal` 是参考值。

| 枚举 | 现实是什么 | 热量怎么表达 | 当前道数 |
|---|---|---|---|
| `fixed` | 按标价牌点，份量固定 | `kcal` 可直接引用 | 284 |
| `weigh` | 称重结算，用户拿多少现场定 | `kcal` 是**参考值**，前端展示须注明「份量以现场称重为准」 | 100 |

> **称重结算的档口**（服务端按此下发 `weigh`）：一楼早餐线（28 道）、二楼健康餐（32 道）、
> 二楼西蜀毛哥麻辣烫的配菜（40 道）。麻辣烫的**汤底与免费米饭不称重**，按份给，
> 这四条单独标 `fixed`。

> **前端据 `pricing_mode === "weigh"` 判断是否加「份量以现场称重为准」的文案**，不需要额外的标记字段。

### C. 可推荐性 `recommendable`

> **这道菜在不在推荐池里。** `false` = **入库可查，但不进推荐**。

当前 `false` 的 78 道全部来自四个档口：**汉堡工厂 37、缙云烧饼 16、炸串精选 14、绍兴小吃 11**。
它们仍然出现在 `/menu` 响应里（用户能查到食堂有什么），但推荐引擎不会给出它们。

> 缺省 `true`。**这是运营口径，不是技术开关**——调整档口的推荐资格只改数据，不改代码。

## 三、需要你判断的 4 个开放问题

### Q1（最要紧）：`pricing_mode` 前端用得上吗？

W2 验收清单的 **I5** 要求：「含称重菜的推荐项，热量以区间或参考值呈现，并注明『份量以现场称重为准』」。
前端要判断「这道菜是不是称重的」，就需要 `pricing_mode` **进 `/menu` 响应**（当前 `toDish` 已经带了）。

**但 `serving_mode` 与 `recommendable` 前端可能用不上**——引擎把「一份即一餐」表达在 `combos` 里了
（`single` 路的 combo 只有一道菜），「不推荐」则是引擎内部过滤的事。

**我的建议**：三个都留着（已经下发了，删反而是破坏性改动），但**在契约里写明各自的使用方**：

| 字段 | 谁用 | 前端要不要用 |
|---|---|---|
| `pricing_mode` | 前端 + 引擎 | **要**（I5 的文案判断） |
| `serving_mode` | 引擎 | 建议不用 |
| `recommendable` | 引擎 | 建议不用；若菜单页想标「不推荐」则可用 |
| `floor` / `stall` | 前端（按楼层/档口分组展示） | 要 |

**你若认为 `serving_mode` / `recommendable` 不该出现在用户端响应里**，请提出——那就得改 `toDish` 投影
（BE-B 的活），并且前端不能用 `recommendable` 隐藏菜。

### Q2：`stall` 的值带楼层前缀，`floor` 是不是冗余？

现在 `stall` 的值是 `"二楼·朝陇阳"`（含楼层前缀），而 `floor` 又单独给了 `2`。**信息重复。**

**我的建议**：保持现状，在契约里写清「`stall` 是展示用的档口全称，含楼层前缀」，并说明
「`floor` 供前端按楼层分组用，不必从 `stall` 里解析字符串」。改 `stall` 的值格式要动数据层，
收益不抵成本。

### Q3：`/menu` 的响应体量——要不要分页或按档口过滤？

v3 有 384 道，`GET /menu?meal=lunch` 现在返回 **356 道**（原型期是 41 道）。每道菜约 300 字节，
响应约 100KB。不算大，但**前端菜单页如果一次性全渲染会卡**。

**建议**（不必本期做，但契约里先留口子）：加两个可选查询参数 `floor` 与 `stall`，
前端按楼层/档口分段拉。要不要现在就加，取决于 FE 的页面设计——**这条最好你先跟 FE-A 对一下**。

### Q4：`reliability` 还会不会是 B？

按 D4 口径，**A 级 = 称重、B 级 = 反推、C 级 = 众包**。v3 的 384 道全部是 B 级（按标准配比反推，
已填 `ingredients` 配料依据）。`ingredients` 按契约**不进响应**，所以前端拿不到依据细节。

**要澄清的是**：D4 说「A / B 级用同一套渲染」，所以前端不需要区分 A/B。那 `reliability` 这个字段
**还有必要下发吗**？现在留着无害（前端不用），但如果将来要「只展示 A 级」的策略，它就有用了。

**我的建议**：留着，在契约里注明「前端当前不据此分支渲染（见 D4），保留用于数据治理与将来的分级策略」。

## 五、联调暴露的两处契约缺口（2026-11-15 晚，FE-A 在 #59 提出）

> **来源**：FE-A 打通真实接口联调时发现，本草稿只覆盖了 `/menu` 那一侧，
> **推荐响应与档案接口还有两处缺口**。他已在 §6 登记为阻塞，PD 拍板了范围（本期做），
> 需要你按附录 C 定契约。**这两处都是「新增字段 / 新增端点」，按附录 C 第 3 条属于兼容变更**
> ——新增字段直接加，旧前端忽略即可，无过渡期。

### 缺口 1：`ComboDish` 没有称重标记，前端无法满足 W2 验收 I5

**现象**：推荐响应的 `ComboDish` 只有营养字段，没有 `pricing_mode`，
前端拿到一套组合后**无法识别哪几道菜要展示「份量以现场称重为准」**。

**为什么这是必须的**：W2 验收 I5 写着「含称重菜的推荐项，热量以区间或参考值呈现，
并注明『份量以现场称重为准』」。称重的有 100 道（一楼早餐 28 + 健康餐 32 + 麻辣烫配菜 40）——
**推荐页会大量命中**，前端没有判据就做不了这个提示。

**建议改法（两级，兼容）**：

```ts
export interface ComboDish {
  // …现有字段不动…
  /** 这道菜的结算方式，与 Dish.pricing_mode 同义。缺省按 "fixed" 处理 */
  pricing_mode?: PricingMode;
}

export interface Combo {
  // …现有字段不动…
  /**
   * 本套里是否含称重结算的菜。true 时前端须在热量旁注明「份量以现场称重为准」。
   * 服务端算好，前端不必遍历 dishes 判断。
   */
  has_weighed_dish?: boolean;
}
```

**为什么给两级**：`ComboDish.pricing_mode` 让前端能定位到**具体哪一道**是称重的（要逐道标注时用）；
`Combo.has_weighed_dish` 让前端**一行判断**就能决定要不要显示提示（大多数场景够用）。
服务端算好组合级标记，前端不必遍历——推荐页一次渲染几十套组合，这个遍历是白给的开销。

**归属**：`shared/src/types.ts`（`/shared/` 归 BE-B）+ `server/src/engines/recommend.ts` 与
`server/src/routes/recommendations.ts`（归 BE-A）。**你先定契约，再分给两边实现。**

### 缺口 2：没有删除档案的端点，合规要求的「删除入口」落不了地

**现象**：API.md §2.2 只有 `POST /profiles` 与 `GET /profiles/me`，**没有删除档案的端点**。
前端不能自造接口删数据，W2 清单 C6 与 W3 A3 的前端入口无法落地。

**PD 已拍板：本期做。** 依据是 README「合规边界」第 3 条——
「涉及用户身体数据（身高 / 体重 / 年龄）按个人信息处理，仅存必要字段，**提供删除入口**」。
这是硬要求，不是可选项。

**建议的端点与语义**：

```
DELETE /api/v1/profiles/me?session_id=...
```

| 情况 | 响应 |
|---|---|
| 删除成功 | `204 No Content` |
| 档案不存在 | `404`（与 `GET /profiles/me` 一致） |

**语义（需要你确认）**：**连带删除该 session 名下的全部 `meal-logs`**。

> 理由：合规上「删除入口」的本意是让用户能**清掉自己的个人数据**。只删档案、留着
> 按 `session_id` 关联的用餐记录，不算清干净——那些记录同样能定位到个人。
> 代价是删完该用户的 `insights` 统计会归零，这是删除的应有之义。

**若你认为该只删档案**，请在定稿时写明；前端会按契约加二次确认，说明会删什么。

### 这两条的优先级

缺口 1 卡住 **W2 验收 I5**，缺口 2 卡住 **W2 清单 C6 与 W3 清单 A3**。
两项都是**新增**，按附录 C 第 3 条属于兼容变更，不需要过渡期，
但**都要在 v3 切上线前落地**——否则 384 道真实菜单推上去之后，推荐页对 100 道称重菜
给不出「份量以现场称重为准」的提示，而用户在自选线看到的份量与热量对不上。
