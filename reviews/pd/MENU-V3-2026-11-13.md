## 1. 诊断：现有架构的假设是什么，和现实差在哪

现有推荐引擎（`server/src/engines/recommend.ts`）的核心假设是：

```
一餐 = 主食(staple) + 主菜(protein) + 素菜(veg | soup | fruit)
```

这个假设对**一楼自选快餐**成立。但实测菜单里 384 道菜分属三种完全不同的「一餐」形态：

| 形态 | 道数 | 现实是什么 | 现有引擎会怎么错 |
|---|---|---|---|
| `plate` 一楼自选线 | 49 | 用户自己拿盘，选几样菜配饭。**一份 = 一盘**，不是组合 | 拆成三件套推荐，用户拿到的是「建议」不是「可点的东西」 |
| `single` 成品餐（**含一楼 8 道面点窗口与白米饭**） | 259 | 点一碗面 / 一盒饭就是**一整餐** | 再配主食 → 「青椒肉丝盖浇饭 + 红烧肉 + 炒青菜」，双主食 |
| `component` 轻食 + 麻辣烫（配菜 / 汤底 / 免费米饭） | 76 | 自己在配菜柜里挑几样配主食 | 轻食可以组合，但麻辣烫缺「汤底 + 主食」，跟轻食不是一回事 |

实测把 v3 直接灌进现有引擎，**3 条测试立刻红**：

```
FAIL  最多 3 套，字段齐全
FAIL  遵守档案里的忌口：不吃辣时组合里没有 spicy 菜
FAIL  午晚按 v1.2.2：每套必须含主食、主菜、素菜
```

**结论：不是数据错了，是「一餐由什么构成」这个模型错了。**
数据（`server/data/menu-seed.v3.json`）已就绪并通过全部数据体检；缺的是模型。

## 2. 目标架构

### 2.1 给菜品加「份量形态」

```
一餐 = 若干个 serving_mode 相同的菜品，按该形态的规则组成
```

**这是唯一需要新增的概念。** 不新增第三种「组合类型」，不拆 category。

### 2.2 类型定义（BE-B 写，`shared/src/types.ts`）

```ts
/**
 * 份量形态：一道菜在一餐里扮演什么角色。
 * - plate    ：一楼自选线。用户自己拿盘选几样（产品口径：不计价、不可单点）
 * - single   ：独立成品餐。一份就是一餐（盖浇饭、拌面、汤面、汉堡、烧饼）
 * - component：可选组件。自由组合（轻食食材、麻辣烫配菜）
 */
export type ServingMode = 'plate' | 'single' | 'component';

export interface Dish {
  // …现有字段不动，但 price_yuan 要删掉（见 §3）…
  serving_mode?: ServingMode;  // 缺省按 'single' 处理
  recommendable?: boolean;     // 缺省 true；false = 入库但不进推荐池
  floor?: 1 | 2;               // 楼层
  stall?: string;              // 档口名，如「二楼·朝陇阳」
}
```

**兼容性要求**：`serving_mode` / `recommendable` 必须是**可选字段**。
`menu-seed.v3.json` 里这批字段目前是「治理字段」——`seed.ts` 逐字段 INSERT，不写这几列，
所以在 BE-B 改完之前它们不会进库。这是有意的：**先让引擎能读，再让种子能写**，两步分开合。

### 2.3 数据层（BE-B 写）

| 文件 | 改动 |
|---|---|
| `server/src/data/db.ts` | dishes 表：**删 `price_yuan` 列**，加 4 列 `floor INTEGER` / `stall TEXT` / `serving_mode TEXT` / `recommendable INTEGER` |
| `server/src/data/seed.ts` | `INSERT` 去掉 price_yuan、补上 4 列；`SEED_PATH` 指向 `menu-seed.v3.json`（**建议在引擎适配合入后再改这一行**） |
| `server/src/data/dishes.ts` | `toDish` 投影：去掉 price_yuan、带出 4 个新字段 |

**SQLite 迁移注意**：dishes 表已有生产数据，`ALTER TABLE ADD COLUMN` 要幂等
（先查 `PRAGMA table_info(dishes)` 再决定是否执行），不能每次 `npm run seed` 都报错。
删列在 SQLite 里要重建表，**注意保留已有数据**。

### 2.4 推荐引擎（BE-A 写，`server/src/engines/recommend.ts`）

#### 候选池

```ts
const pool = getDishesByMeal(meal, false).filter((d) => d.recommendable !== false);
```

#### 三路分流

```
pool
 ├─ serving_mode === 'component' → 组合路（现有三件套逻辑基本可用）
 ├─ serving_mode === 'single'   → 单份路（每道菜自成一套）
 └─ serving_mode === 'plate'    → 不进 combos，走「建议配盘」
```

**① 组合路（component）**

- 轻食（32 道）：主食组件 + 蛋白组件 + 蔬菜组件，沿用现有 `staple × protein × veg` 结构
- 麻辣烫（44 道）：**三段式已完整**——汤底（番茄 / 金汤 / 微辣，3 选 1）+ 主食（免费米饭 / 粉丝 / 面 / 粉）
  + 配菜（40 道任选）。与轻食不同，麻辣烫需要引擎支持「选一个汤底」的组合结构：
  汤底是必选项，配菜是可选多项，汤底本身参与热量与钠的计算
- 忌口过滤、份量、去重逻辑沿用现有实现
- **辣度由汤底表达**：配菜本身不标 `spicy`，只有「微辣汤底」带 `spicy`。这样「不吃辣」的档案拿到的是番茄/金汤底的组合，而不是整个麻辣烫档口被排除

**② 单份路（single）—— 本次改动的主体**

每道成品菜自成一套：

```ts
combos: [{ id, dishes: [该道菜], totals: { kcal, protein_g, … }, notes }]
```

评分**沿用现有 `penalty` 逻辑**（热量偏离、蛋白不足/过量、目标类型加分），
不要另起一套评分——两套评分会让「套数」「贴合度」两条既有验收口径失去意义。

关键约束：
- **不得再给它配主食**（盖浇饭/拌面本身已含碳水）
- 主食互不相同的去重规则**不适用**（一套只有一道菜），改为「不重复同一道菜」
- 「每餐 3 套」的要求对单份路同样适用：从单份路候选里取 3 套

**③ 建议配盘路（plate）—— 本次最需要产品判断的部分**

一楼自选线只给**餐食建议**。用户要的不是「点哪个」，而是「今天该吃什么」。

建议形态：按 target 推荐「一荤 + 一素 + 主食」的**内容建议**（菜名列表），
不进入 `combos`（`combos` 语义是「可点的组合」，一楼菜不可单点，塞进去会误导前端）。

两种实现方式，请 BE-A 选一种并说明理由：
- **A**：在推荐响应里新增字段（如 `plate_suggestion: { dishes: string[], text: string }`）
  → 需要 `shared/` 加类型 + `docs/API.md` 改契约（归 BE-B / pigQAQ）
- **B**：复用现有 `notice` 字段拼一段文字建议，不改契约
  → 改动最小，但前端拿不到结构化菜名

**PD 倾向 A**：产品上「建议配盘」需要能点进具体菜名，前端要能渲染成卡片并跳到菜品详情；
B 方案只能给一段文字，产品价值低很多。但 A 要动契约，BE-A 需与 BE-B 协调排期。
