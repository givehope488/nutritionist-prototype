# 项目架构文档

> 版本 v1.0（2026-11-03）。本文档是模块边界与技术决策的唯一事实源，修改须经团队评审并在「决策记录」追加条目。

## 1. 总体架构

```
┌─────────────────────────────────────────────────┐
│  用户端 H5（Vue 3，移动优先）                      │
│  建档 / 目标与忌口 / 单餐推荐 / 回填 / 反馈 / 历史 │
└───────────────────────┬─────────────────────────┘
                        │ REST / JSON（docs/API.md）
┌───────────────────────┴─────────────────────────┐
│  服务端 API（Express + TS）                       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐         │
│  │ 营养计算  │ │ 推荐引擎  │ │ 理由生成  │         │
│  │ 引擎      │ │ 过滤+组合 │ │ template │         │
│  │          │ │ +评分    │ │ /llm 可换 │         │
│  └──────────┘ └──────────┘ └──────────┘         │
│  ┌──────────┐ ┌──────────┐                      │
│  │ 用户档案  │ │ 用餐记录  │                      │
│  └──────────┘ └──────────┘                      │
└───────┬─────────────────────────────┬───────────┘
        │                             │
┌───────┴──────────┐   ┌──────────────┴───────────┐
│  数据库           │   │  管理端（复用后端 API）    │
│  dishes / profiles│   │  菜品 CRUD · 数据校准     │
│  meal_logs / ...  │   │  新菜提报 · 修订历史      │
└──────────────────┘   └──────────────────────────┘
```

**核心原则：服务端是营养计算的口径唯一来源。** 前端只负责收集输入、渲染输出，不做任何营养数值计算。所有公式（BMR / TDEE / 目标热量 / 蛋白分配 / 推荐评分）只存在于 `server/src/engines/` 一处，保证多端一致、可单测、可审计。

## 2. 模块职责

| 模块 | 位置 | 职责 | 不做什么 |
|---|---|---|---|
| 营养计算引擎 | `server/src/engines/nutrition.ts` | Mifflin-St Jeor BMR、活动系数、目标系数、蛋白分配、餐次切分 | 不读数据库，纯函数 |
| 推荐引擎 | `server/src/engines/recommender.ts` | 忌口硬过滤 → 组合枚举（含"补小荤"两阶段）→ 评分排序 → 取 3 套 | 不生成文案 |
| 理由生成 | `server/src/llm/` | 双引擎：template（规则模板）/ llm（润色），含输出校验与降级 | 不产生新数字、新菜名（见 §4） |
| 用户档案 | `server/src/services/profile.ts` | 建档、未成年校验、目标与忌口管理 | 不做账号体系（首版匿名 session） |
| 用餐记录 | `server/src/services/meallog.ts` | 回填、汇总、采纳判定、统计 | 不修改推荐结果 |
| 菜品管理 | `server/src/admin/` | 菜品 CRUD、可信度分级、修订历史留痕 | 生产环境禁止直连数据库改数据 |

## 3. 推荐链路数据流

```
POST /api/v1/recommendations
  ├─ 1. 载入用户档案（或请求内联档案）
  ├─ 2. nutrition.ts 计算：BMR → TDEE → 目标热量 → 本餐目标（kcal/P/F/C/钠）
  ├─ 3. recommender.ts：
  │     a. 按餐段取菜品池，忌口/过敏硬过滤（含未成年目标降级）
  │     b. 枚举 主食×主菜×素菜×汤 组合（早/午晚两种结构）
  │     c. 两阶段：对 Top50 基线补一个"小荤"（kcal≤260 或 fat≤12g）
  │     d. 评分：热量贴合×120 + 热量不足额外罚 + 蛋白达成度
  │        + 脂肪占比(阈值42%) + 钠(参考线1600mg) + 蔬菜加分
  │     e. 取 3 套：主菜组合不重复、主食互不相同（池小则放宽）
  ├─ 4. llm/ 生成理由（见 §4）
  └─ 5. 返回：combos[] + 每套 nutrition 合计 + reason + engine 标记
```

算法参数与权重随代码迁移自已验证原型（含单元测试基线：5 类人群、忌口场景、极端条件），迁移时**测试用例先行**，断言口径不变。

## 4. LLM 文案层设计（重点）

**定位**：数值由代码计算并写入结构化结果，LLM 只做「把结构化结果说成人话」。**LLM 无权引入任何新数字或新菜名。**

### 4.1 输入契约

```json
{
  "engine": "llm",
  "combo": { "dishes": [{"id": "s01", "name": "白米饭"}, ...], "kcal": 910, "protein_g": 32, ... },
  "target": { "kcal": 913, "protein_g": 31, ... },
  "meal": "lunch",
  "goal": "health"
}
```

### 4.2 输出校验（服务端，逐条硬断言）

| # | 校验规则 | 失败处置 |
|---|---|---|
| V1 | 输出中出现的菜品名 ⊆ 输入 combo.dishes 的菜名集合 | 降级 template |
| V2 | 输出中出现的数字 ⊆ 输入数值集合（kcal/蛋白/脂肪/差值等） | 降级 template |
| V3 | 长度 40~120 字，单段 | 降级 template |
| V4 | 不含医疗承诺词（治疗/疗效/降血压等违禁清单） | 降级 template |
| V5 | LLM 调用超时（>3s）或异常 | 降级 template |

降级不报错给前端：响应中 `engine` 字段如实标记实际使用 `llm` / `template`，用于统计降级率（目标 <10%）。**模板引擎是永久兜底，不是过渡方案。**

### 4.3 切换

配置项 `TEXT_ENGINE = 'template' | 'llm'`（env），默认 `llm` 上线灰度，降级率超标可一键回退。

## 5. 数据模型（首版）

```
dishes        id*, name, category, portion_label, meals[], kcal, protein_g,
              fat_g, carbs_g, sodium_mg, price_yuan, tags[], drink,
              reliability(A/B/C), status, updated_at
dish_revisions  id*, dish_id, changed_fields{}, operator, reason, created_at   # 修订留痕
profiles      session_id*, sex, height_cm, weight_kg, age, activity,
              goal, avoid[], default_meal, created_at, updated_at
meal_logs     id*(uuid，客户端生成，幂等), session_id, date, meal,
              items[{dish_id, servings}], adopted_combo(可空), totals{},
              created_at
rec_logs      id*, session_id, request_hash, engine, degraded(bool),
              latency_ms, created_at                             # LLM 观测
```

首版不做账号体系：`session_id` 由前端生成并持久化（localStorage），换设备即新用户。若后续需要跨设备，再升级为轻登录（学号或微信授权），数据模型已预留。

## 6. 部署

首版单机：`docker compose`（node 服务 + SQLite 卷 + Caddy 反代），校园内网或云主机均可。量级预估（单校区数千用户、日活数百）远未到需要水平扩展的程度，**不为不存在的规模做设计**。

## 7. 决策记录（ADR 简版）

| # | 决策 | 理由 | 备选与放弃原因 |
|---|---|---|---|
| D1 | 所有营养计算在服务端 | 口径唯一、可测试、可审计；前端渲染不受公式变更影响 | 前端计算：原型可行，多端后必然漂移 |
| D2 | SQLite 起步 | 单文件零运维，ORM 隔离方言，量大再迁 PG | 直接 PG：运维成本前置，当前无必要 |
| D3 | LLM 仅润色、白名单校验 | 从结构上杜绝幻觉数字/编造菜名，模板兜底保证可用性 | 端到端生成：需额外约束且验收困难 |
| D4 | 匿名 session 而非账号 | 降低建档流失；健康数据最小化采集 | 学号登录：登录墙会砍掉大半建档完成率 |
| D5 | 菜品数据可信度三级标注 | 份量口径是最大数据风险，分级让前端展示策略有依据 | 统一精度：会造成虚假精确 |
| D6 | 管理端复用后端 API + 简单前端 | 1 人即可运营，避免独立系统 | 独立管理后台：当前规模下过度设计 |

## 8. 风险与技术债登记

| 风险 | 等级 | 应对 |
|---|---|---|
| 反推数据与真实偏差大，用户感知"不准" | 高 | 可信度分级展示 + 上线前抽 10 道菜称重校准 |
| LLM 降级率超标影响体验 | 中 | rec_logs 观测 + 一键回退 template |
| 食堂菜品季节性变化未同步 | 中 | 管理端"下架/上新"流程 + 每周巡检 |
| session 丢失导致记录丢失 | 低 | 文档明示 + 后续版本升级轻登录 |
